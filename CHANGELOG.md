# Changelog

This file tracks real changes to this repository. For the rules on how entries here should be written, see CHANGELOG_TEMPLATE.md.

### Initial script, flexible query input, and project setup (round one)

1. Added `Start-EdiscoveryInvestigation-NoExport.ps1`, a PowerShell script that creates a Microsoft Purview eDiscovery case scoped to a single mailbox, using the minimum Graph modules needed (`Microsoft.Graph.Authentication`, `Microsoft.Graph.Security`, `Microsoft.Graph.Beta.Security`). It optionally places a preservation hold and starts an estimate and statistics run for review in the Purview portal, without configuring an export, since PAYG export is not available.
2. Replaced the script's fixed financial-activity search query with four ways to supply the content search query: a raw KQL string through `-ContentQuery`, a simple keyword or phrase list through `-Keywords` with a configurable AND/OR join via `-KeywordOperator`, the original financial-activity query kept as an opt-in preset through `-UseFinancialTemplate`, and a fully interactive prompt that runs when none of the above are supplied, including when the script is invoked with no parameters at all. The interactive path also prompts for tenant, target mailbox, case name, and hold preference when those are not passed as parameters, so the script is usable end to end with zero arguments. This replaces the previous behavior of always defaulting to the fixed financial-activity query.
3. Added `.github/workflows/release.yml` so pushing a version tag such as `v1.0.0` automatically builds a GitHub Release with the script attached as a download and auto-generated release notes, with a manual `workflow_dispatch` fallback for re-running a release against an existing tag. The workflow runs on a single Ubuntu runner since the script needs no per-platform build step, and scopes write permissions to only the release job.
4. Added the standard community-health files used across this account's public projects: `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG_TEMPLATE.md`, and this `CHANGELOG.md`, along with `.github/PULL_REQUEST_TEMPLATE.md` and `.github/ISSUE_TEMPLATE/bug_report.md` and `feature_request.md`, adapted for this project from the private template repository.
5. Added a `LICENSE` file under the Business Source License 1.1, which converts automatically to the GNU General Public License v3.0 on the change date specified in the license text, with an additional use grant permitting use of the script for eDiscovery, investigation, and compliance work.
6. Rewrote `README.md` to document the new query-input options with an example for each, and to explain how to get the latest version of the script from GitHub: cloning the repository, downloading the newest tagged release asset, or fetching the script directly from the `main` branch.

### Hold documentation clarified (round two)

7. Clarified in the script header and in `README.md` that `-PlaceHold` (and its interactive y/N prompt) is independent of how the search query was built. The behavior was already decoupled from `-UseFinancialTemplate`, but the only usage examples showed the two together, which implied a preservation hold required the financial-activity preset. Updated the examples so a hold is shown alongside `-Keywords` instead, and the financial-activity example no longer includes a hold, to make the independence explicit.

### Case search creation race fixed (round three)

8. Fixed a failure where `New-MgSecurityCaseEdiscoveryCaseSearch` could return a 409 conflict with the message "Object reference not set to an instance of an object" immediately after `New-MgSecurityCaseEdiscoveryCase` succeeded. This happens because Purview provisions the case's backend container asynchronously, so the case is not always immediately ready to accept a search. The Microsoft Graph PowerShell SDK cmdlets do not reliably honor `$ErrorActionPreference = 'Stop'` for this kind of service error, so the script previously continued past the failed call with an empty `$search` object and failed later, much less clearly, on `Cannot bind argument to parameter 'EdiscoverySearchId' because it is an empty string`. Added an `Invoke-WithRetry` helper that retries a scriptblock up to five times with exponential backoff (starting at five seconds) when the error text matches the known provisioning-race signature, and applied it to case search creation, the mailbox source addition, and both legal hold calls, since each one runs against the same just-created case. Every wrapped cmdlet call now also passes `-ErrorAction Stop` explicitly rather than relying on the global preference, and the script checks that `$case.Id`, `$search.Id`, and `$hold.Id` are non-empty immediately after each create, throwing a clear error if not, so any remaining failure stops the script at the point of the actual problem instead of cascading into an unrelated-looking error further down.

### Preservation hold made idempotent (round four)

9. Fixed `New-MgBetaSecurityCaseEdiscoveryCaseLegalHold` failing with a 409 conflict, "A compliance policy with name '...' already exists," when `-PlaceHold` was used against a mailbox that already had a preservation hold from an earlier run. Legal hold names are compliance policy names, which are not scoped to a single case, so re-running the script against the same target mailbox always hit this once a hold existed. The script now calls `Get-MgBetaSecurityCaseEdiscoveryCaseLegalHold` before creating anything, and if a hold with the expected display name is already there, it reuses that hold's Id and skips creation instead of failing. A narrower try/catch around both the create call and the mailbox-source-add call also treats an "already exists" conflict from a concurrent run as success and re-fetches or skips accordingly, rather than aborting. This also fixed a related bug in the `Invoke-WithRetry` helper added in round three, which matched any error text containing the literal string "409" as a transient provisioning race and retried it five times before giving up; every Graph HTTP error includes "Status: 409" in its message, so permanent conflicts like "already exists" were being retried uselessly instead of failing fast. The retry match is now scoped to the actual provisioning-race signature ("Object reference not set") only.

### Compliance search name collisions fixed (round five)

10. Fixed `New-MgSecurityCaseEdiscoveryCaseSearch` failing with a 409 conflict, "The compliance search object 'Search - user@example.com' already exists within your organization," on any second run against the same mailbox. Unlike legal hold names, the script had no reuse handling for search names at all, and the fixed `"Search - $TargetUpn"` name is a compliance search object name, which (like legal hold names) is unique tenant-wide rather than scoped to the case, so it collided with a search left behind by a prior run, including one against a different case. Added `New-UniqueSearchDisplayName`, which appends an 8-character GUID-derived suffix to the search display name so each run gets a distinct name by default, and wrapped the search-creation call in a loop (up to five attempts) that, on an "already exists" conflict, generates another unique name and retries instead of aborting the whole script.

### Hold creation no longer aborts the run; smart quotes normalized out of KQL (round six)

11. Fixed `-PlaceHold` still aborting the whole run with "Could not create or locate the preservation hold. Aborting." even after round four's reuse logic. The reuse check in round four looked up an existing hold by display name scoped to the *current* case (`Get-MgBetaSecurityCaseEdiscoveryCaseLegalHold -EdiscoveryCaseId $case.Id`), but hold display names are compliance policy names and are unique tenant-wide, not scoped to a case. When an earlier run had created a same-named hold under a *different* case, the create call still failed with 409 "already exists," the concurrent-creation catch block's re-fetch (also case-scoped) found nothing, and the script threw and aborted despite the case and search already existing. Replaced the fixed-name lookup/create/reuse logic with `New-UniqueHoldDisplayName`, the same GUID-suffix approach round five added for search names, so each run's hold gets a distinct name and does not depend on a case-scoped lookup finding a hold that may live elsewhere. The create call is now wrapped in the same "retry with a new name on an already-exists conflict, up to five attempts" loop already used for searches. If hold creation still cannot succeed after that (including for non-conflict errors), the script no longer throws immediately: it reports the error and prompts "Continue WITHOUT a preservation hold? (y/N)". Answering yes clears `-PlaceHold` and continues to the estimate/statistics run and summary with no hold in place; answering no throws and aborts, preserving the option to stop deliberately when a hold is required.
12. Fixed curly/smart quotes (U+2018/2019/201C/201D and related Unicode variants) ending up in the final KQL query instead of straight ASCII quotes, which Purview's KQL parser does not treat as phrase delimiters, silently breaking phrase matching and unbalancing the query's quote count. This happens whenever a phrase is typed or pasted with quotes already applied by Word, Outlook, a browser, or a terminal's own autocorrect, before it ever reaches the script's own quoting logic in `ConvertTo-KqlFromKeywords`. Added `ConvertTo-AsciiQuotes`, which maps the common smart-quote code points to straight `'` and `"`, and applied it to every text entry point before it becomes part of `$FinalQuery`: each `-Keywords` element, `-ContentQuery`, and both the raw-KQL and keyword-list branches of the interactive prompt. `ConvertTo-KqlFromKeywords` was also changed to strip any quotes already present on a (now-normalized) term before deciding whether to re-wrap it in straight quotes based on whitespace, rather than only skipping the wrap when the term was already found matching a straight-quote pattern; this prevents both doubled quoting (`"""term"""`) and the mismatched straight/curly quoting that caused the original report.

### Stray outer single-quote wrap fixed (round seven)

13. Fixed the actual defect behind the previously reported broken query: the whole `$FinalQuery`, not just its individual terms, was ending up wrapped in a single leading and trailing straight quote (`'(...)'`) once submitted to Purview, which is not valid KQL syntax anywhere and broke the search. Round six's smart-quote normalization fixed the curly double quotes around each term but did not address this outer wrap, since it is a different character (a straight single quote, not a curly double quote) at a different position (around the whole expression, not per-term). Single quotes carry no meaning in KQL at all - the parser only recognizes double quotes for phrase matching - so a leading/trailing `'` around the entire query is always copy-paste artifact, most likely from a command-line-style example (including this script's own usage examples, which show `-ContentQuery` values wrapped in single quotes as PowerShell's own argument-quoting syntax) being pasted somewhere that takes the text completely literally instead of stripping that shell quoting - an interactive prompt, a portal search box, or a `-ContentQuery` value passed as a literal string. Added `Remove-OuterQuoteWrap`, which trims the query and strips one matching leading/trailing straight single quote if both are present, and applied it once to `$FinalQuery` immediately after it is resolved, so it catches the artifact regardless of which of the four query sources (`-ContentQuery`, `-Keywords`, `-UseFinancialTemplate`, or the interactive prompt) produced it.
